# Dashboard 设计规格

**状态：** 已完成需求确认，等待规格审阅。

**适用环境：** 仅 staging。production 在统一工资账本切换获得单独批准前，不提供此页面或接口。

## 1. 目标与边界

Dashboard 为管理员提供同一页的两类信息：

1. 店铺经营：已批准收入产生的原始营业额和员工提成。
2. 员工工资：已生效账本中的收入、罚款、预支、调整、净额，以及实际已付款金额。

它的目标是按月份、店铺和员工比较表现，并能回到员工账本流水核对每一个工资数字。

Dashboard 不会写入、修改、删除或冲正任何工资记录，也不会改变 Telegram、工资审批或发薪周期逻辑。

### 不在第一版范围内

- production 部署或 production 统一账本切换；
- 第三方图表库、CDN 或新的前端框架；
- 新数据库表、预计算月度汇总表或后台定时汇总任务；
- 历史月份的“当前待付工资”分析；
- 自动发薪、付款凭证、邮件、员工收款确认或个人发薪周期功能；
- 账户、银行卡、USDT 地址或付款证明等敏感资料的展示。

## 2. 已确认的产品决策

| 决策 | 结论 |
| --- | --- |
| 发布顺序 | 先在 staging 开发和验收；production 账本切换后才单独批准上线 |
| 首页目标 | 同时支持经营管理和工资管理 |
| 页面结构 | 双层一页看板，而不是两个分离标签或一个高密度长页 |
| 默认筛选 | 当前店铺、当前月、全部员工 |
| 多店铺 | 支持；只允许管理员有权限的店铺 |
| 多币种 | 永远按币种分组显示，禁止跨币种相加 |
| 图表技术 | 原生 SVG 和现有 CSS；不增加依赖 |
| 工资权威来源 | `payroll_entries.amount_micros` |
| 原始营业额来源 | 已批准 `income_records` 的收入字段；只作经营指标，不参与工资净额计算 |
| 实际付款来源 | `salary_records`；只表示已付款历史，不抵消账本收入 |

## 3. 页面结构

后台增加“数据看板”标签；在 staging 登录后默认打开该标签。现有店铺、员工、收入、工资、预支、考勤、缺勤、请假和日志标签保留不变。

```text
筛选：店铺｜月份或日期范围｜员工

经营概况
  原始营业额｜员工提成｜员工人数
  月度营业额与提成趋势

工资概况
  账本净额｜罚款扣减｜预支扣减｜实际已付款
  收入、罚款、预支、奖金与调整构成图

员工对比
  柱状图：按当前排序指标比较员工
  表格：员工｜营业额｜提成｜罚款｜预支｜账本净额｜实际已付款｜查看流水

员工账本明细
  在点击“查看流水”后显示；使用当前筛选范围并分页
```

所有图表同时提供同一数据的表格或数值标签。图表不是唯一数据来源，管理员能够使用键盘、屏幕阅读器或表格核对金额。

### 筛选行为

- **店铺：** 默认当前后台店铺；可多选有权限的店铺。
- **月份或日期范围：** 默认当前月。日期输入是店铺当地日期，开始和结束日期均为用户可见的包含边界。
- **员工：** 默认全部；选择员工后，经营、工资和明细都只显示该员工。
- **排序：** 员工对比表可按任一金额列排序；图表使用同一排序结果。

第一版不提供“按账本类型筛选”的全局开关，避免让营业额、实际付款与只筛选部分工资类型的净额混在同一口径中。工资构成图和明细会完整展示类型差异。

## 4. 指标口径

所有 API 金额使用整数 micros 返回，即一个货币单位等于 `1,000,000` micros。浏览器只负责格式化显示，不做金额求和。

| 指标 | 数据来源 | 计算 | 归属时间 | 说明 |
| --- | --- | --- | --- | --- |
| 原始营业额 | `income_records` | 所有 `type='income'` 的 `income` 行级转换后求和 | `approved_at` | 顾客消费或原始营业额；不是员工工资 |
| 员工提成 | `payroll_entries` | `type='income'` 的 `amount_micros` 求和 | `effective_at` | 已生效的员工提成 |
| 罚款扣减 | `payroll_entries` | `type='fine'` 的负数 micros 求和 | `effective_at` | 保持负号展示，表示扣减 |
| 预支扣减 | `payroll_entries` | `type='advance'` 的负数 micros 求和 | `effective_at` | 保持负号展示，表示扣减 |
| 奖金与调整 | `payroll_entries` | `bonus`、`adjustment`、`negative_carry`、`reversal` 分类型求和 | `effective_at` | 在工资构成和明细中显示，全部计入净额 |
| 账本净额 | `payroll_entries` | 该范围内全部 `amount_micros` 求和 | `effective_at` | 该时段已生效的工资变化，不等于实际支付金额 |
| 实际已付款 | `salary_records` | `amount` 行级换算为 micros 后求和 | `approved_at` | 该时段管理员批准的实际付款；不从账本净额中扣除 |
| 员工人数 | `store_members` | 当前筛选店铺内、且符合员工筛选条件的 active 成员数 | 当前状态 | 用于经营概况，不按历史回溯成员状态 |

同一时间范围内，“账本净额”和“实际已付款”可以不同：前者按收入或扣款发生时间统计，后者按付款批准时间统计。页面必须使用这两个完整名称，不能把任一项简称为“工资”。

“当前待付工资”是从每名员工的当前 `cycle_start` 到现在的实时快照，不是历史月份指标，因此不在第一版 Dashboard 出现。

## 5. 时区、币种与范围

工资账本使用左闭右开范围：

```text
timestamp >= start_iso AND timestamp < end_iso
```

对于单店铺，`2026-07-01` 至 `2026-07-31` 表示该店铺时区内从 7 月 1 日 00:00 至 8 月 1 日 00:00。

对于多店铺，不能把所有店铺套进当前店铺的单一 UTC 区间。后端必须为每个选中店铺生成自己的：

```text
store_id, start_iso, end_iso
```

并使用相应店铺自己的范围查询收入、账本和付款历史。月度趋势也按每店铺本地月生成桶，再按币种聚合。

后端绝不把不同 `currency` 的金额相加。API 和页面以 `currency` 为最高金额分组；同币种的多个店铺可以在同一组内汇总。

## 6. API 与权限契约

Dashboard 延续现有后台 URL 和会话模式：

```text
GET /api/admin/stores/:storeId/dashboard
GET /api/admin/stores/:storeId/dashboard/entries
```

共同查询参数：

```text
stores=STORE_A,STORE_B
date_from=YYYY-MM-DD
date_to=YYYY-MM-DD
employee=TELEGRAM_ID        (可选；省略或 all 表示全部)
```

`storeId` 是当前后台选择的店铺，也是路由权限入口。`stores` 可以包含多个店铺，但服务端必须逐个验证当前管理员在每个店铺都是 active `admin` 或 `owner`，全局管理员保留现有全店权限。

### 主看板响应

主看板接口只返回聚合结果、月度趋势和员工对比，不返回完整流水：

```json
{
  "ok": true,
  "filters": {
    "store_ids": ["STORE_A"],
    "date_from": "2026-07-01",
    "date_to": "2026-07-31",
    "employee": null
  },
  "groups": [
    {
      "currency": "₫",
      "summary": {
        "gross_income_micros": 0,
        "commission_micros": 0,
        "fine_micros": 0,
        "advance_micros": 0,
        "net_payroll_micros": 0,
        "paid_salary_micros": 0,
        "employee_count": 0
      },
      "months": [],
      "employees": []
    }
  ]
}
```

`months` 按本地月桶返回营业额、提成和账本净额。`employees` 返回员工名称、身份、上述可比较金额及各类型账本金额；返回顺序由请求的合法排序参数确定。

### 流水明细响应

`/entries` 只读取 `payroll_entries`，支持相同筛选和 `entries_page` 分页。必须返回：

```text
entry_id, store_id, telegram_id, display_name, type, amount_micros,
currency, effective_at, source, source_id, created_at,
reverses_entry_id
```

页面要把 `reversal` 明确标识为冲正，保留带符号金额，不得把冲正行隐藏、合并或改写。`metadata_json` 不通过 Dashboard API 返回，避免未来扩展字段意外暴露敏感上下文。

### 错误与环境限制

- 未登录：`401 unauthorized`。
- 无店铺权限：`403 forbidden`。
- 无效日期、未知员工或非法排序参数：`400` 和机器可读错误码。
- 无数据：`200`，金额为零、数组为空；不把无数据当错误。
- 数据库异常：`500 server_error`，保留结构化错误日志但不记录敏感支付信息。
- production：Dashboard 标签和接口都不可用；实现通过现有环境识别逻辑拒绝，而不是回退到旧工资公式。

## 7. 后端与前端边界

| 位置 | 职责 |
| --- | --- |
| `src/dashboard.js` | Dashboard 输入校验、每店铺时区范围、聚合 SQL、金额结果映射；不渲染 HTML |
| `src/admin-api.js` | 路由、管理员会话、店铺权限和 JSON 响应；不复制聚合 SQL |
| `src/admin-page.js` | 新标签、筛选状态、加载 API、原生 SVG、数据表、明细抽屉或区域；不自行计算金额 |
| `test/dashboard.test.js` | 口径、时区、币种、权限和 API 回归 |

聚合必须由数据库完成。后端可以为每个请求构造店铺时间范围和月度桶的参数化 CTE，但不能先读出所有流水交给浏览器计算，也不能对每个员工单独执行一条查询。

## 8. 图表与可访问性

第一版使用原生 SVG：

1. 月度营业额与提成趋势；
2. 收入、罚款、预支、奖金和调整的工资构成；
3. 员工对比柱状图。

每张图必须：

- 使用同一 API 返回的整数 micros；
- 有文字标题、币种和数值标签；
- 提供同一数据的表格；
- 空数据时显示明确的“该筛选范围没有数据”，不绘制误导性零值图；
- 能显示负数柱或负数标签；
- 在手机屏幕保持可横向查看或退化为表格，不裁掉数值。

## 9. 验收与测试

### 自动化测试

新增测试至少覆盖：

1. 单店铺中营业额、提成、罚款、预支、调整、冲正与账本净额的精确 micros 汇总。
2. 实际已付款不改变账本净额，且按 `salary_records.approved_at` 统计。
3. 同币种店铺可汇总，不同币种必须分成两个结果组。
4. 东京与另一不同时区店铺在月初、月末 UTC 边界的归属正确。
5. 多店铺请求为每个店铺使用其自身日期范围。
6. 管理员不能查询无权限店铺，即使把店铺 ID 手写进 URL。
7. 无数据、负数、冲正和员工筛选的 JSON 响应正确。
8. 主看板聚合不因员工人数产生 N+1 查询。
9. 后台页面含 Dashboard 标签、筛选、图表数据表和流水入口；production 不显示该功能。
10. 现有测试全部继续通过。

### staging 验收

1. 使用已回填、对账完成的 staging 账本。
2. 选择一个店铺和一个月，人工把 Dashboard 汇总与账本明细求和核对。
3. 选择多店铺，验证币种分组和每店铺本地月边界。
4. 选择有罚款、预支、冲正和实际付款的员工，核对表格、图表和明细一致。
5. 用无权限管理员或篡改 URL 验证 `403`。
6. 验证 production 不出现 Dashboard 页面或 API。
7. 运行 `npm run check`、`npm test`、`git diff --check`。
