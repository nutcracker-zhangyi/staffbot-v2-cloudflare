# 考勤汇总与缺席罚款审批设计

## 目标

在现有 StaffBot 管理后台的考勤页面中，一次展示多名员工的考勤汇总，并在员工缺席时自动发起罚款审批。管理员批准后才产生正式罚款，罚款继续复用现有收入和工资扣减流程。

本设计以最小改动为原则：保留现有店铺、员工、日期筛选，保留现有考勤明细表和收入罚款编辑能力，不重做管理后台。

## 已确认的业务规则

- 员工默认每天都应上班，包括周末。
- 只有已批准请假才不算缺席；待审批或被驳回的请假不豁免缺席。
- 实际工作天数按存在签到记录的不同营业日期计算，同一天签到和签退只算一天。
- 迟到天数按迟到签到记录对应的不同营业日期计算。
- 缺席是员工应上班，但没有签到且没有已批准请假。
- 历史缺席仍可按员工加入日期、签到和已批准请假计算；缺席审批和罚款只从店铺启用缺席罚款功能的当天开始，不补发启用前的审批或罚款。
- 缺席罚款金额按店铺设置，可编辑。越南盾店铺默认配置值为 `1.5`，实际金额为 `1,500,000₫`，沿用现有迟到和早退罚款的金额换算规则。
- 系统发现缺席后只创建待审批记录，不直接扣款。
- 管理员批准后才生成正式罚款；管理员驳回后仍保留缺席事实，但不产生罚款。
- 正式缺席罚款和其他收入罚款一样，可以在现有收入页面修改。
- 缺席之后若同一天的请假获批，待审批缺席自动取消；已经批准的缺席罚款保留原始金额，但实际罚款自动改为 `0`。

## 方案选择

### 采用：独立缺席审批记录

新增专门的缺席审批表，保存缺席日期、建议罚款、审批状态和正式收入罚款的关联。该表同时承担缺席事实记录和罚款审批状态的职责。

该方案比复用签退审批或收入审批多一张小表，但不会把不同业务语义混在一起，能够直接支持去重、请假取消、审计和按营业日期统计。

### 不采用：复用签退审批

签退审批代表员工已经签到但需要确认早退，缺席代表员工完全没有签到。复用会让查询、通知文案和审批动作产生歧义。

### 不采用：复用收入审批

收入审批没有缺席日期、请假取消和缺席唯一性等语义。强行复用会增加特殊分支，最终改动并不会更小。

## 数据设计

### 店铺设置

在 `stores` 中增加：

- `absence_fine`：缺席罚款配置值，金额解释与 `late_fine`、`early_leave_fine` 一致。
- `absence_fine_enabled_at`：当前一轮启用缺席罚款的时间；为空表示关闭。

管理后台店铺设置增加“启用缺席罚款”开关和“缺席罚款”输入框。首次启用或关闭后重新启用时，系统记录新的启用时间，防止补算停用期间或更早的缺席。

### 缺席审批表

新增 `absence_fine_requests`，至少包含：

- 请求 ID
- 店铺 ID
- 员工 Telegram ID
- 营业日期
- 原始建议罚款
- 当前建议罚款
- 状态：`pending`、`approved`、`rejected` 或 `cancelled`
- 创建和通知时间
- 审批时间、管理员 ID、驳回或取消原因
- 批准后生成的收入记录 ID

数据库对“店铺 ID、员工 ID、营业日期”建立唯一约束。同一次缺席无论定时任务运行多少次，都只能产生一条审批。

## 定时发现缺席

在 Worker 中增加 Cloudflare Cron Trigger，每小时运行一次。Cron 使用 UTC，但处理时按每个店铺自己的时区判断。

现有业务日期逻辑把当地时间中午 12 点以前视为前一个营业日，因此任务在每个店铺当地时间次日 12 点后的第一次运行中结算前一个营业日。

每个符合结算条件的店铺执行：

1. 确定尚未完整检查且不早于本轮启用日期的营业日。
2. 查询该营业日需要工作的启用员工。
3. 排除有签到记录的员工。
4. 排除有已批准请假的员工。
5. 为剩余员工幂等创建缺席审批。
6. 向该店铺管理员发送 Telegram 审批通知。

任务不依赖管理员打开页面。任务失败后，下一小时重新扫描尚未完成的日期；唯一约束防止重复审批和重复通知。

## Telegram 审批

管理员通知包含：

- 店铺名称
- 员工姓名
- 缺席日期
- 建议罚款金额
- “批准罚款”按钮
- “驳回”按钮

回调数据使用紧凑请求 ID，确保不超过 Telegram 的 64 字节限制。

批准时，系统以一个原子数据库操作完成：

1. 只允许把仍为 `pending` 的审批改为 `approved`。
2. 生成 `income_records` 正式罚款，类型为 `fine`，来源为 `attendance_absence`。
3. 保存生成的收入记录 ID、审批人和审批时间。

重复点击不重复生成罚款。驳回只更新审批状态，不生成收入记录。

## 请假获批后的联动

管理员批准请假时，系统查找相同店铺、员工和请假日期的缺席审批：

- `pending`：改为 `cancelled`，原因记录为请假已批准，不再允许批准罚款。
- `approved`：关联收入记录的 `fine` 改为 `0`，`original_fine` 保持不变；缺席审批改为 `cancelled`，原审批人和审批时间继续保留。
- `rejected`：改为 `cancelled`，不产生财务修改，原审批人、审批时间和驳回原因继续保留。

这样能够保持“已批准请假不算缺席”的规则，同时保留完整审计信息。

## 考勤页面

### 页面结构

保留现有深色视觉体系和筛选区，页面依次显示：

1. 店铺、开始日期、结束日期和可选员工筛选。
2. 五张整体汇总卡。
3. 员工考勤汇总表。
4. 现有待审批签退、考勤记录和已驳回签退明细。

五张汇总卡为：

- 实际工作天数
- 迟到天数
- 缺席天数
- 已批准请假天数
- 考勤罚款总金额

罚款总金额包含迟到、早退和缺席产生的实际罚款。被驳回、取消或实际金额已改为 `0` 的罚款不计入。

### 多员工汇总表

表格一行对应一个“店铺 + 员工”，列为：

- 店铺，多店铺筛选时显示
- 员工姓名
- 实际工作天数
- 迟到天数
- 缺席天数
- 已批准请假天数
- 罚款总金额
- 查看明细

查询必须以店铺员工表为起点，再关联考勤、请假、缺席和罚款数据。完全没有签到记录的员工也必须出现在列表中。

选择全部员工时，顶部卡片按人天合计。例如两名员工各工作一天，实际工作天数显示 `2`。选择单个员工时，卡片和列表都只显示该员工。

点击“查看明细”后，页面复用现有员工筛选并加载该员工的下方明细，不增加新的详情页面。

### 视觉要求

- 复用现有颜色变量、圆角、边框、字体和间距，不引入新的 UI 库。
- 五张汇总卡使用一致高度、清晰的标题与大号数字；罚款金额保留千分位。
- 汇总表使用现有斑马纹、悬停状态和可点击排序表头。
- 缺席、请假等状态仅使用克制的文字或小型状态标签，不使用大面积高饱和颜色。
- 员工姓名保持可读，内部 ID 继续紧凑显示。
- 桌面端优先在一屏内浏览关键列；窄屏保持卡片自适应换行，表格使用现有横向滚动，不挤压文字。
- 不在列表中展开所有明细，避免页面过长；通过“查看明细”按需查看。

## 统计口径与查询范围

所有统计在服务端针对完整筛选结果计算，不从当前分页的数据相加。

- 实际工作天数：不同“店铺、员工、营业日期”的签到数量。
- 迟到天数：上述签到中 `late = 1` 的不同营业日期数量。
- 缺席天数：从员工加入日期起，在已经结束的营业日中，没有签到且没有已批准请假的日期数量。该统计可以覆盖功能启用前的历史日期，但历史日期不会补发审批或罚款。
- 请假天数：状态为 `approved` 的不同请假日期数量。
- 罚款总额：属于迟到、早退或缺席来源的正式收入罚款实际 `fine` 合计，并按对应考勤或缺席营业日期纳入日期筛选。

## 错误与并发处理

- Cron 重复运行依靠数据库唯一约束去重。
- 多位管理员同时审批时，只有第一个对 `pending` 状态的更新成功。
- 批准状态与正式收入罚款在同一个数据库批处理中写入，避免只审批但没产生罚款。
- 通知发送失败不创建第二条审批；后续任务可以根据未通知状态重发。
- 店铺关闭缺席罚款后，不再创建新审批，但保留既有记录和统计。

## 验收标准

1. 选择店铺和日期后，一次查询可看到该范围内所有启用员工，包括完全没有签到的员工。
2. 每名员工的工作、迟到、缺席、请假和罚款统计符合上述口径。
3. 顶部总计与员工列表合计一致，且不受分页影响。
4. 启用前的历史缺席可以显示在统计中，但不产生缺席审批或自动补罚。
5. 次日当地时间 12 点后的任务为缺席员工创建一次审批并通知店铺管理员。
6. 重复执行任务不会重复通知或重复生成罚款。
7. 管理员批准后产生可编辑的正式罚款；驳回后不产生罚款。
8. 后批准的请假会取消待审批缺席，或把已批准缺席罚款的实际金额改为 `0`。
9. 多管理员并发审批不会产生两条罚款。
10. 页面延续现有深色风格，在桌面和窄屏下均可清晰使用。
