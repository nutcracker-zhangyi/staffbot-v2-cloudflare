# USDT 收款二维码设计

日期：2026-07-29

## 目标

员工选择 USDT 收款时，可以：

- 只填写钱包地址；
- 只上传二维码；
- 同时提供钱包地址和二维码。

三种情况都必须进入现有个人发薪流程。二维码用于管理员付款，不替代管理员
付款后上传的付款凭证。

## 已确认决定

- USDT 地址和二维码至少提供一种。
- 员工可以同时保存地址和二维码。
- 二维码通过 Telegram 上传。
- 二维码保存在私有 R2，不生成公共 URL。
- 工资记录保存生成当时的二维码版本，员工以后修改资料不影响旧工资。
- Telegram 和管理后台都允许有权限的管理员查看二维码。
- 当前处于 `awaiting_admin_payment` 且尚未开始拆分的工资允许补充二维码，
  但不重新计算固定工资金额、周期或截止点。

## 不在本次范围

- 不识别二维码内的钱包地址。
- 不校验链类型、代币合约、地址格式或二维码内容。
- 不生成新的二维码。
- 不把二维码附加到财务确认邮件。
- 不开放公共图片地址。
- 不改变管理员付款凭证、工资金额或发薪周期规则。

## 用户流程

### 选择收款方式

员工仍先使用 Telegram 按钮选择银行卡、USDT 和现金。

如果选择 USDT，继续显示三个按钮：

1. `输入钱包地址`
2. `上传二维码`
3. `地址和二维码`

选择地址时，员工输入一条非空文本。选择二维码时，员工发送一张 Telegram
图片。选择两者时，先输入地址，再上传二维码。

完成条件：

- 仅地址：地址非空；
- 仅二维码：二维码已成功写入 R2 和数据库；
- 两者：地址和二维码都已完成。

员工发送普通文件、空文本或非图片内容时，系统保留当前状态并提示重新发送。

### 修改已有资料

员工可以从尚未付款的工资消息重新进入“确认/修改收款信息”：

- `awaiting_employee_details` 可以修改；
- `awaiting_admin_payment` 且尚未保存付款拆分时可以修改；
- 已有付款拆分、已上传凭证、等待确认、争议或已确认后不能修改该笔工资快照。

“已开始付款拆分”的数据库判断为 `current_admin_id IS NOT NULL`。只要该字段
已有值，即使某个拆分金额为 0，也不得再修改收款方式、地址或二维码。

修改当前资料会更新以后工资使用的收款资料。只有仍允许修改的当前工资同步
更新快照，固定工资金额、周期和截止点保持不变。

## 数据模型

### 新表 `payroll_payment_qr_codes`

每次成功上传生成一行，不覆盖旧行：

| 字段 | 规则 |
| --- | --- |
| `qr_id` | 非空主键 |
| `store_id` | 所属店铺 |
| `telegram_id` | 所属员工 |
| `object_key` | 私有 R2 对象键，唯一 |
| `telegram_file_id` | 供同一机器人重新发送 |
| `mime_type` | 只允许支持的图片 MIME |
| `size_bytes` | 正整数，最大 10 MiB |
| `uploaded_at` | 上传完成时间 |
| `superseded_at` | 被新二维码替换的时间，可为空 |

索引覆盖：

- `store_id + telegram_id + uploaded_at`
- 唯一 `object_key`
- `store_id + telegram_id` 的未替换二维码部分唯一索引

### `payroll_payment_profiles`

新增可空字段：

- `usdt_qr_id`

该字段指向员工当前使用的二维码版本。选择不再使用 USDT 或选择仅地址时，
当前二维码指针清空，但历史二维码行和 R2 对象不删除。

上传新二维码、改为仅地址或不再使用 USDT 时，原二维码行写入
`superseded_at`。任意时刻每名员工在一家店铺最多只有一个未被替换的二维码。

### `payroll_disbursements`

新增可空字段：

- `usdt_qr_id_snapshot`

工资生成或仍允许修改收款资料时，复制当前二维码版本 ID。工资进入管理员拆分
后，该字段不可再改。旧工资因此始终引用当时的二维码。

迁移必须保持现有付款资料和工资记录有效：新增字段默认为 `NULL`，现有
USDT 地址继续单独满足有效资料条件。

## R2 对象

对象键使用不可预测、按店铺和员工隔离的版本化路径：

```text
payroll-payment-qr/<store>/<employee>/<qr-id>.<ext>
```

规则：

- 上传前验证 Telegram 图片、MIME 和大小；
- 先写 R2，再写二维码行和资料指针；
- 数据库写入失败时删除本次新对象；
- 新上传不覆盖或删除旧对象；
- 日志不得记录对象内容、Telegram 文件 ID、地址全文或公开 URL。

历史对象暂不自动清理。以后如需清理，只能删除没有被当前资料或任何工资快照
引用的对象。

## 工资结算与有效性

USDT 收款方式的有效条件改为：

```text
accepts_usdt = true
AND (usdt_details 非空 OR usdt_qr_id 有效)
```

生成工资时复制：

- `usdt_details_snapshot`
- `usdt_qr_id_snapshot`

二维码不存在不影响只使用银行卡或现金的员工。仅二维码资料不能被文本掩码
函数当作地址处理；列表显示“已提供二维码”。

## Telegram 管理员体验

员工保存资料后，管理员通知显示：

- 银行卡：地址、未使用；
- USDT：地址、二维码、地址和二维码、未使用；
- 现金：使用、未使用。

如存在 USDT 二维码，机器人在文字通知后向每位有权限的店铺管理员发送二维码
图片和工资 ID。优先复用 `telegram_file_id`；发送失败不回滚已保存资料，
管理员仍可从后台查看。

管理员进入付款拆分前可以看到员工接受的方式。二维码不改变拆分规则：
银行卡、USDT、现金的金额仍必须为非负整数 micros，合计等于固定工资快照。

## 管理后台

自动工资列表只返回：

- `has_usdt_qr`
- 已掩码的钱包地址

详情接口返回二维码存在状态和一个认证读取路径，不返回 R2 对象键或公共 URL。

新增私有读取路由：

```text
GET /api/admin/stores/:storeId/payroll/:payrollId/usdt-qr
```

授权条件：

- 已登录管理员；
- 管理员属于工资所属店铺；
- 工资的 `usdt_qr_id_snapshot` 属于同一店铺和员工。

响应使用正确图片 MIME、`Cache-Control: private, no-store` 和现有安全响应头。

## 安全与故障处理

- R2 bucket 保持私有，不配置公共域名。
- 跨店铺管理员不能查看二维码。
- 不能通过猜测 `qr_id` 或对象键绕过工资权限。
- R2 上传失败时不写数据库。
- R2 成功但数据库失败时删除新对象。
- Telegram 管理员图片发送失败时保留资料，并记录不含敏感字段的固定错误。
- 二维码更新与资料指针、工资快照更新必须使用同一 D1 batch。
- 已开始付款拆分时，拒绝修改该笔工资的地址、二维码或接受方式。

## 测试策略

### 单元和数据库测试

- 仅地址、仅二维码、两者都有均通过校验；
- 地址和二维码都没有时拒绝；
- 非 USDT 方法不要求二维码；
- 迁移保留现有地址资料和工资；
- 新二维码版本不覆盖旧行；
- 工资快照引用生成时的版本；
- 资料更新不改写已开始付款的工资；
- R2 成功、D1 失败时删除新对象。

### Telegram 流程测试

- 三种 USDT 资料模式都由按钮进入；
- 仅二维码不要求输入地址；
- 两者模式按地址、图片顺序完成；
- 非图片和超限图片被拒绝且状态保留；
- 管理员收到二维码，发送失败不回滚资料；
- 当前未拆分工资可以补充二维码且金额不变。

### 管理后台和权限测试

- 列表不暴露对象键或 Telegram 文件 ID；
- 同店管理员可以读取工资快照二维码；
- 跨店管理员和未登录用户被拒绝；
- 响应没有公开缓存；
- production 管理后台不出现 staging 存储配置。
