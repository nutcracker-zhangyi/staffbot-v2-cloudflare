# 管理员手机 PWA 完整设计规格

- 日期：2026-07-29
- 状态：设计已确认，等待书面规格复核
- 目标系统：`staffbot-v2-cloudflare`
- 首个发布范围：仅管理员使用

## 1. 背景

当前系统的员工操作主要在 Telegram 内完成，管理员既要接收通知，也要在 Telegram 或桌面管理后台中处理审批和工资。Telegram 适合收消息，但不适合连续查看资料、上传多张付款回执、比较记录或追溯一次工资的完整处理过程。现有 `/admin` 后台保留了大量宽表格，适合电脑端查询和导出，不适合手机上的任务处理。

本次新增一个可安装到手机桌面的管理端 PWA。它与现有 Worker 共用后端、D1、R2、登录会话和业务规则，不另建一套业务系统。Telegram 在管理员侧退回到“通知和登录验证码入口”，员工侧现有流程保持不变。

## 2. 目标与成功标准

### 2.1 产品目标

1. 管理员可在手机上完成首个发布范围内的全部审批与工资操作。
2. 每项任务都有明确状态、当前处理人、操作时间和历史记录。
3. 每次工资付款都可追溯到固定工资快照、付款拆分、付款回执、管理员和员工反馈。
4. 多名管理员同时工作时，不会重复审批或重复付款。
5. PWA、现有 `/admin` 和 Telegram 共用同一份业务数据，不形成双重账本。

### 2.2 首个发布的验收结果

满足以下条件才算首个管理员 PWA 发布完成：

- 管理员可通过 Telegram 验证码登录 `/manage`。
- Telegram 的管理员任务通知可打开对应的 PWA 任务。
- 收入与罚款、请假与缺勤、预支工资可在手机上审批。
- 工资记录可被领取、查看、拆分付款、上传多张回执并提交。
- 员工确认或提出问题后，管理员可看到结果；有问题时可形成新的付款版本。
- 已提交的工资付款证据不可覆盖或删除。
- 多管理员任务领取、租约过期和负责人强制接管有效且有审计记录。
- iPhone Safari 和 Android Chrome 上完成真实设备验收。
- 所有自动化检查通过，并完成 staging 全流程回归。
- 未得到明确的“发布 live”指令前，不合并或部署到生产环境。

## 3. 范围

### 3.1 首个产品发布包含

- 管理员专用 PWA 路由 `/manage`
- Telegram ID 加一次性验证码登录
- Telegram 任务摘要和“去处理”深链接
- 待办优先首页
- 收入与罚款审批
- 请假与缺勤审批
- 预支工资审批
- 工资记录与工资档案详情
- 通用任务领取、续租、释放和强制接管
- 工资付款拆分
- 按付款方式上传多张回执
- 提交付款并通知员工
- 员工确认工资或反馈付款问题
- 付款问题后的新付款版本
- 完整审计记录和历史证据查看
- PWA 安装、移动端适配和离线提示

### 3.2 首个产品发布不包含

- 员工 PWA
- 员工管理
- 店铺设置
- 考勤详情管理
- 新的业务 Dashboard
- 完整系统日志管理界面
- 原生 iOS 或 Android 应用
- 邮件通知或邮件回执
- 重写现有工资计算规则
- 重写员工 Telegram 流程
- 删除或替换现有 `/admin`

员工继续在 Telegram 提交收入、请假、收款信息、预支工资申请，并确认工资或反馈付款问题。现有 `/admin` 继续承担电脑端宽表查询、CSV 导出和应急管理。

## 4. 方案选择

### 4.1 采用的方案

在现有 Cloudflare Worker 内增加 `/manage` PWA：

- 与现有项目共同构建和部署。
- 共用现有 D1、R2、Telegram Bot 和权限模型。
- 后端把稳定业务逻辑提取为可被 Telegram、`/admin` 和 `/manage` 共同调用的服务。
- PWA 使用面向手机任务处理的页面，不直接缩小或复制桌面宽表。
- 暂不引入独立 React、Vue 或 Cloudflare Pages 项目。

### 4.2 未采用的方案

1. **只把 `/admin` 改为响应式**
   改动表面上较少，但现有页面以宽表查询为中心，无法自然支持领取任务、连续付款、多回执和版本追溯。

2. **建立独立前端项目**
   前后端边界更明显，但当前规模下会增加部署、跨域、登录状态和环境配置成本。

3. **开发原生手机应用**
   会增加应用商店发布、双平台开发和升级成本，当前需求不需要使用原生能力到这个程度。

4. **用邮件保存工资证据**
   邮件不是首个发布的必要条件。D1 保存结构化记录，R2 保存私有回执，Telegram 负责通知，已经能形成可追溯证据链。

## 5. 用户、权限和数据隔离

### 5.1 用户角色

- 店铺管理员：只能查看和处理其有权限店铺的数据。
- 店铺负责人：拥有店铺管理员权限，并可强制接管本店任务。
- 全局管理员：按现有权限模型查看和处理获准范围内的数据。
- 员工：不能进入 `/manage`；继续使用 Telegram。

### 5.2 权限规则

- 每个读取、审批、领取、上传和提交接口都必须在服务端验证权限。
- 前端隐藏按钮只用于界面表达，不能代替服务端授权。
- 任务、工资、员工、付款版本和回执读取必须校验店铺范围。
- R2 不提供公开文件 URL。回执只能通过已登录且通过授权检查的 Worker 接口读取。
- 任何跨店铺访问均返回无权限，不返回可用于推断其他店铺数据的详细信息。

## 6. 登录、会话和深链接

### 6.1 登录流程

1. 管理员打开 `/manage`，输入自己的 Telegram ID。
2. 后端确认该 Telegram ID 对应有效管理员。
3. 系统向该管理员的 Telegram 发送一次性验证码。
4. 管理员在 PWA 输入验证码。
5. 验证成功后建立安全会话 Cookie，并进入待办首页。

沿用现有管理员会话的安全属性和失效机制。验证码只能短时使用、单次使用，并限制重复发送和错误尝试。

### 6.2 任务深链接

- Telegram 管理员通知包含任务摘要和“去处理”按钮。
- 按钮指向 `/manage` 内的具体任务，而不是通用首页。
- 未登录时先进入验证码登录，成功后返回原任务。
- 已完成的任务仍可打开，但只显示结果、处理人和处理时间，不显示已失效操作。
- 无权限或任务已被移到其他授权范围时，显示明确但不泄露数据的提示。

## 7. 信息架构与导航

底部导航固定为四项：

1. **待办**：默认首页，按紧急程度排序，可切换店铺。
2. **审批**：集中查看收入与罚款、请假与缺勤、预支工资。
3. **工资**：查看工资记录、待付款任务和付款历史。
4. **更多**：店铺切换、当前账号和退出登录。

后续产品发布可在“更多”中增加员工管理、店铺设置、考勤详情、Dashboard 和日志，但首个发布不预留空白假入口。

### 7.1 待办首页

每张待办卡至少显示：

- 任务类型
- 员工
- 店铺
- 关键金额或日期
- 提交时间
- 当前状态
- 当前处理人或“未领取”
- 紧急程度

默认先显示即将超时、等待付款或员工已反馈问题的任务，再显示普通待审批任务。筛选条件至少包括店铺和任务类型。

### 7.2 审批列表

审批页按类别分组或切换，支持：

- 待处理、已通过、已拒绝状态筛选
- 店铺筛选
- 员工搜索
- 日期范围

审批详情显示申请原始信息、附件、关联员工和店铺、提交时间、既有相关记录以及审计时间线。拒绝时必须填写原因。

### 7.3 工资列表

工资页以工资记录为入口，显示：

- 员工和店铺
- 工资周期
- 固定工资总额
- 付款状态
- 当前付款版本
- 当前处理人
- 员工确认或问题状态

## 8. 通用任务领取机制

### 8.1 领取规则

- 任何有该任务权限的管理员都可领取未被占用的任务。
- 第一个成功领取者获得编辑权。
- 其他管理员可以查看，但页面只读，并显示处理人和领取时间。
- 领取使用 15 分钟空闲租约。
- 领取者保持任务页活跃时，客户端定期续租。
- 领取者可以主动释放任务。
- 15 分钟无续租后，租约失效，其他管理员可领取。
- 店铺负责人可以强制接管本店任务；全局管理员按现有权限范围处理。
- 强制接管必须记录原处理人、新处理人、原因和时间。

### 8.2 并发控制

领取、续租、释放、强制接管和最终提交均使用服务端条件更新。不能使用“先读取、再无条件更新”的方式判断所有权。

提交操作必须同时验证：

- 任务仍处于可提交状态。
- 当前用户仍拥有有效租约。
- 提交所基于的数据版本未过期。

条件不满足时返回冲突，PWA 刷新最新状态并切换为只读，不自动重复提交。

## 9. 审批流程

收入与罚款、请假与缺勤、预支工资共用一致的处理框架，但继续调用各自现有业务校验。

1. 管理员从待办或审批列表打开详情。
2. 管理员领取任务。
3. 系统显示原始申请、附件和关联信息。
4. 管理员选择通过或拒绝。
5. 拒绝时填写原因。
6. 后端条件更新业务状态并写入审计日志。
7. 系统向员工发送现有 Telegram 结果通知。
8. Telegram 发送失败不回滚已提交的审批；记录失败状态并提供重试入口。

审计内容至少包括任务类型、业务记录 ID、店铺、操作前状态、操作后状态、处理人、处理时间和拒绝原因。

## 10. 工资档案和付款流程

### 10.1 工资档案详情

工资记录先以完整档案方式展示，不直接进入付款表单。详情包括：

- 员工和店铺
- 工资周期起止时间
- 工资截止时间
- 固定工资快照及其构成
- 当前状态
- 员工收款资料
- 当前和历史付款拆分
- 当前和历史付款回执
- 管理员操作时间线
- 员工确认或付款问题记录

工资金额使用既有工资结算规则产生的固定快照。进入付款阶段后，PWA 不重新计算或静默改变这笔工资。

### 10.2 进入付款

管理员点击“领取并开始付款”：

1. 领取工资任务。
2. 创建或恢复当前管理员的草稿付款版本。
3. 进入单页付款表单。

### 10.3 单页付款表单

同一页面包含：

- 固定工资总额
- 银行卡金额
- USDT 金额
- 现金金额
- 每种付款方式的回执上传区
- 图片预览、删除和替换
- 当前处理人和租约状态
- “提交付款并通知员工”按钮

校验规则：

- 银行卡、USDT、现金之和必须严格等于固定工资快照。
- 金额使用系统现有的统一最小单位和精度规则，不能使用浮点近似比较。
- 金额大于零的每种付款方式至少上传一张回执。
- 一种付款方式可上传多张图片。
- 提交前，草稿图片可预览、删除或替换。
- 提交时必须再次验证权限、租约、工资状态、金额合计和回执完整性。

### 10.4 提交与员工通知

提交成功后：

1. 固定本次付款版本、付款拆分和回执。
2. 更新工资当前状态和当前付款版本摘要。
3. 写入审计记录。
4. 向员工 Telegram 发送可追溯的工资通知。
5. 等待员工“确认已收到”或“付款有问题”。

Telegram 通知发送失败时，付款提交保持成功。系统保存通知失败和重试状态，在 PWA 显示异常，并允许有权限的管理员重试通知。

### 10.5 员工确认

员工确认后，记录至少包括：

- 员工
- 店铺
- 工资周期
- 工资总额
- 当前付款版本
- 确认时间
- 对应 Telegram 用户

工资档案显示确认结果，任务进入完成状态。已完成记录仍可读取证据，但不能修改。

### 10.6 员工反馈付款问题

员工点击“付款有问题”后：

1. 当前付款版本保留并标记员工反馈问题。
2. 工资任务重新进入管理员待办。
3. 管理员领取任务并查看原付款证据和问题记录。
4. 系统创建下一版本的付款草稿。
5. 管理员重新填写付款拆分、上传新回执并提交。
6. 员工对新版本再次确认或反馈问题。

旧版本和旧回执永远保留。最新被员工确认的版本作为当前结果展示，所有历史版本仍可展开查看。

## 11. 付款证据不可变规则

### 11.1 草稿阶段

- 草稿付款版本只能由当前有效领取者编辑。
- 草稿回执可以删除和替换。
- 上传成功但尚未最终提交的对象必须带草稿付款版本标识。
- 领取失效后，原管理员不能继续修改该草稿。

### 11.2 提交后

- 已提交的付款版本不能编辑、覆盖或删除。
- 已提交的付款拆分不能改变。
- 已提交的 R2 回执对象不能通过业务接口删除。
- 修正只能创建新付款版本，不能修改旧版本。
- 每个版本独立保存提交人、提交时间、拆分、回执和员工反馈。

### 11.3 放弃草稿清理

为避免未提交图片长期占用 R2：

- 租约失效或管理员主动放弃后，草稿付款版本标记为已放弃。
- 已放弃且连续 7 天未恢复的草稿回执可由定时清理任务删除。
- 清理前再次确认付款版本仍为草稿或已放弃，且没有被任何已提交版本引用。
- 已提交回执不进入自动清理范围。
- 清理操作记录对象键、付款草稿、原因和时间。

该规则只清理未形成付款证据的草稿，不影响历史证据留存。

## 12. 数据设计

### 12.1 数据源原则

现有业务表继续作为唯一业务数据源。PWA 不复制员工、店铺、收入、罚款、请假、预支工资或工资账本。

现有工资付款汇总记录继续保存“当前状态和当前结果”，以兼容 Telegram、`/admin` 和既有查询；新增付款版本表保存不可变历史。

### 12.2 通用任务领取表

新增通用任务领取记录，概念字段为：

| 字段 | 用途 |
|---|---|
| `task_type` | 收入、罚款、请假、缺勤、预支工资或工资付款 |
| `task_id` | 对应业务记录 ID |
| `store_id` | 用于授权和隔离 |
| `claimed_by` | 当前领取管理员 |
| `claimed_at` | 本次领取时间 |
| `lease_expires_at` | 租约到期时间 |
| `updated_at` | 最后续租或变更时间 |

同一业务任务只能存在一个有效领取状态。过期记录可保留用于审计，但领取判断以服务端当前时间和有效租约为准。

### 12.3 工资付款版本表

新增工资付款版本，例如 `payroll_payment_attempts`：

| 字段 | 用途 |
|---|---|
| `id` | 付款版本 ID |
| `payroll_id` | 工资记录 |
| `version` | 从 1 递增的版本号 |
| `status` | 草稿、已提交、员工确认、员工反馈问题、已放弃 |
| `bank_amount` | 本版本银行卡金额 |
| `usdt_amount` | 本版本 USDT 金额 |
| `cash_amount` | 本版本现金金额 |
| `submitted_by` | 提交管理员 |
| `submitted_at` | 提交时间 |
| `employee_response` | 确认或付款问题 |
| `employee_responded_at` | 员工反馈时间 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

`payroll_id + version` 唯一。付款版本一旦提交，金额字段只能读取。

### 12.4 回执关联

工资回执记录增加付款版本关联：

- 每张回执属于一个 `payment_attempt_id`。
- 保存付款方式、R2 对象键、原始文件名、MIME 类型、大小、上传人和上传时间。
- 已提交版本的回执不允许重新指向其他版本。
- 回执读取接口先通过付款版本找到工资和店铺，再执行授权。

### 12.5 审计

沿用 `admin_audit_logs`，增加或规范以下事件：

- 领取、续租、释放、租约过期、强制接管
- 审批通过、审批拒绝
- 创建付款草稿
- 上传、删除草稿回执
- 提交付款
- Telegram 通知失败和重试
- 员工确认或反馈问题
- 创建新付款版本
- 清理放弃的草稿回执

## 13. 既有数据迁移

迁移以不丢失现有工资和回执为首要原则：

1. 为已有工资付款数据创建或回填版本 1。
2. 能从现有工资付款汇总恢复的拆分和状态写入版本 1。
3. 现有回执尽可能关联到对应的版本 1。
4. 保留现有 `superseded_at`、R2 对象和审计信息。
5. 无法可靠恢复的旧付款拆分显示“历史明细不可用”，不能根据总额猜测。
6. 迁移后现有 Telegram 和 `/admin` 查询仍可通过当前工资付款汇总正常工作。
7. 迁移必须可重复检查；不得重复创建同一工资版本。

在 staging 先使用现有测试数据验证回填结果，并对迁移前后工资数量、付款状态、回执数量和对象可读性做对账。

## 14. API 和服务边界

PWA 接口按业务能力组织，而不是直接暴露数据库表：

- 登录、验证码和会话
- 待办查询
- 任务领取、续租、释放和强制接管
- 审批详情及通过/拒绝
- 工资档案查询
- 付款草稿和拆分
- 草稿回执上传、读取和删除
- 付款提交
- 通知状态和重试
- 审计时间线

Telegram、`/admin` 和 `/manage` 共用同一业务服务执行状态变化。稳定的工资计算和员工 Telegram 逻辑不重写，只提取 PWA 必须复用的边界。

所有改变状态的请求带幂等标识。重复点击或网络重试必须返回同一结果，不能生成重复审批、重复付款版本或重复员工通知。

## 15. 一致性和错误处理

### 15.1 提交一致性

- D1 中相关状态更新使用事务能力允许范围内的批处理和条件更新。
- R2 图片先作为草稿上传，最终 D1 提交只引用已成功上传且归属当前草稿的对象。
- 最终提交失败时保留草稿，管理员可修正或重试，不把它显示为已付款。
- 最终提交成功后，付款版本进入不可变状态。

### 15.2 常见错误

- 单张图片上传失败：只重试该图片，不要求重传全部回执。
- 租约失效：停止编辑，刷新任务状态，允许重新领取或只读查看。
- 其他管理员已完成任务：显示最新结果和处理人，不再次提交。
- 金额不相等：在前端即时提示，服务端仍再次校验。
- 回执不完整：指出缺少回执的付款方式。
- Telegram 通知失败：付款不回滚，进入通知异常待办。
- 网络中断：保留页面已填写的非敏感草稿状态，但任何财务操作都必须在线重新验证后提交。
- 重复提交：通过幂等标识和条件状态更新返回首次提交结果。

## 16. PWA 和离线策略

- 支持添加到 iPhone 和 Android 手机桌面。
- Service Worker 只缓存应用外壳、静态样式和必要图标。
- 不缓存工资金额、员工收款资料、回执图片或审批业务响应。
- 离线时显示清晰横幅，并禁用领取、审批、上传和付款提交。
- 恢复网络后重新拉取任务状态和租约，不自动提交离线期间的操作。
- 手机相册和相机上传均需验证。

## 17. Telegram 的职责

### 17.1 管理员侧

Telegram 只负责：

- 登录验证码
- 新任务或异常摘要
- “去处理”深链接
- 必要的处理结果提醒

管理员的实际领取、审批、付款、上传和历史查看在 PWA 完成。

### 17.2 员工侧

员工继续在 Telegram：

- 提交收入
- 申请请假
- 登记或更新收款信息和 USDT 二维码
- 申请预支工资
- 接收工资通知
- 确认收到工资
- 反馈付款问题

## 18. 安全要求

- 验证码短时有效、单次使用，并限制发送频率和错误次数。
- 会话 Cookie 使用现有安全策略，不通过 URL 传递会话凭证。
- 所有写接口进行 CSRF 或同等来源保护。
- 上传限制为允许的图片 MIME 类型、合理文件大小和数量。
- 不信任客户端传入的店铺、工资金额、管理员或对象键。
- R2 对象键由服务端生成。
- 日志不记录验证码、完整会话令牌或不必要的敏感收款资料。
- 回执接口防止通过顺序 ID 或对象键越权枚举。
- 强制接管和财务提交属于高价值审计事件。
- Service Worker 不保存业务数据。
