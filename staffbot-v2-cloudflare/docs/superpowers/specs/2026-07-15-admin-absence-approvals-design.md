# 后台缺勤审批页面设计

## 背景与现状

每天缺勤检查已经把审批保存到 `absence_fine_requests`，并通过 `absence_fine_notifications` 记录各管理员的 Telegram 通知状态。批准和拒绝逻辑也已经存在，但目前只能通过 Telegram 回调调用。

管理后台的“考勤”页面只读取签退审批和考勤记录，没有查询缺勤审批表，也没有网页审批接口。因此当前问题不是记录未保存，而是后台缺少查询、展示和操作入口。

## 目标

新增独立的“缺勤审批”后台导航页，让有权限的管理员能够：

- 查看待审批缺勤。
- 在后台批准或拒绝缺勤罚款。
- 查看已批准、已拒绝和已取消的完整历史。
- 查看 Telegram 通知发送情况。
- 使用现有店铺、员工、日期、排序和分页能力。
- 与 Telegram 共用同一套审批规则，保证不会重复罚款。

## 不在本次范围

- 不改变每日缺勤发现时间或 Cron。
- 不改变缺勤罚款金额的店铺设置。
- 不允许在批准前修改建议罚款。
- 不新增数据库表或迁移。
- 不删除或替换 Telegram 审批。
- 不新增批量批准功能。
- 不为已经发送的 Telegram 消息同步修改按钮或正文。

## 方案选择

### 采用：独立“缺勤审批”导航页

缺勤审批拥有独立状态、日期、通知和罚款语义。单独页面能让管理员集中处理待办，同时避免与签退审批混淆。页面仍复用现有后台组件和筛选状态，不引入新框架。

### 不采用：放入现有“考勤”页面

改动较少，但考勤页面已经包含汇总卡、员工列表、签退审批和考勤明细。继续加入缺勤审批会让页面过长，且“签退审批”和“缺勤审批”的动作含义不同。

### 不采用：混入签退审批表

两类请求的数据表、字段和批准后写入逻辑不同。合并表格需要大量条件分支，用户也难以辨认正在批准早退还是缺勤。

## 页面结构

顶部导航增加“缺勤审批”，保持现有深色主题、间距、圆角、表格、按钮和窄屏横向滚动行为。

页面从上到下包含：

### 筛选区

复用现有后台筛选逻辑：

- 店铺，可选择管理员有权访问的一个或多个店铺。
- 员工，可选择全部或单个员工。
- 开始日期和结束日期，按店铺当地营业日期过滤。
- 状态：全部、待审批、已批准、已拒绝、已取消。

切换筛选后，待审批、历史、汇总和导出链接使用同一过滤条件。页面拥有独立的分页和排序状态，不影响其他导航页。

### 汇总卡

显示完整筛选结果的：

- 待审批数量。
- 已批准数量。
- 已拒绝数量。
- 已取消数量。
- 已批准罚款总额。

罚款总额读取关联 `income_records.fine` 的当前实际值，确保批准后人工修改罚款时后台汇总同步变化。多店铺存在不同币种时按币种分组显示，例如 `₫3,000,000 · $20`，不把不同货币直接相加。

### 待审批缺勤

字段为：

- 店铺。
- 员工姓名。
- 缺勤营业日期。
- 建议罚款。
- 创建时间。
- Telegram 通知状态。
- 操作。

通知状态由 `absence_fine_notifications` 聚合显示：

- 已发送数量 / 通知管理员总数。
- 尚无通知行时显示“未入队”。
- 存在失败或等待重试时显示“待重试”，不在主表展开完整错误文本。

每行提供：

- “批准罚款”：弹出确认提示，直接使用当前建议金额。
- “拒绝”：弹出必填原因输入；空白原因不提交。

### 审批历史

一个统一表格显示 `approved`、`rejected` 和 `cancelled`：

- 店铺和员工。
- 缺勤日期。
- 状态。
- 建议罚款。
- 当前实际罚款。
- 审批管理员。
- 审批时间。
- 拒绝或取消原因。
- 关联罚款记录 ID。

历史按审批时间或创建时间倒序。已批准罚款仍在现有收入/罚款记录页面编辑，本页只显示当前值，不重复提供编辑入口。

## 后台 API

新增店铺级路由：

- `GET /api/admin/stores/:storeId/absence`
- `POST /api/admin/stores/:storeId/absence/:requestId/approve`
- `POST /api/admin/stores/:storeId/absence/:requestId/reject`

### 查询接口

GET 使用现有 `adminFilters`、`listPagedRows`、排序白名单和店铺权限范围，返回：

- `pending`：待审批列表。
- `history`：已批准、已拒绝、已取消列表。
- `summary`：各状态数量和按币种分组的实际罚款总额。
- `filters`。
- `pagination.pending` 和 `pagination.history`。

查询关联：

- `store_members`、`users` 获取员工显示名。
- `stores` 获取店铺名、时区和币种。
- `income_records` 获取已批准罚款当前实际金额。
- 聚合后的 `absence_fine_notifications` 获取通知状态。

汇总必须针对完整过滤结果计算，不能从当前分页行相加。

### 批准接口

1. 先验证后台会话对 URL 中店铺有管理员权限。
2. 验证请求真实属于该店铺，防止使用其他店铺的请求 ID。
3. 调用现有 `approveAbsenceFineRequest` 核心逻辑。
4. 仅 `pending` 可以转为 `approved`。
5. 在原子批处理中生成一条 `income_records` 缺勤罚款并关联记录 ID。
6. 返回处理后的状态和记录 ID。

不复制批准 SQL，Telegram 与后台必须调用同一个业务函数。

### 拒绝接口

后台请求体为：

```json
{ "reason": "拒绝原因" }
```

规则：

- 去除首尾空白后不能为空，否则返回 HTTP 400。
- 验证请求属于 URL 店铺。
- 复用拒绝核心函数，但允许传入后台填写的原因。
- Telegram 调用继续使用现有默认原因，不改变当前 Telegram 交互。
- 仅 `pending` 可以转为 `rejected`。

## 权限与并发

- 页面导航只对现有后台管理员显示；具体请求继续由后台会话和店铺管理员权限保护。
- 多店铺查询只能包含当前管理员有权访问的店铺。
- 操作按钮携带记录真实 `store_id`，服务端仍再次验证，不能只依赖前端。
- Telegram 和后台同时批准或拒绝时，现有条件更新保证只有第一个对 `pending` 的决策成功。
- 后处理者收到“已经处理”结果，不能生成第二条罚款。
- 后台批准后旧 Telegram 按钮仍可能显示，但点击只会提示记录已经处理。
- 已批准请假导致的 `cancelled` 请求不能再从后台批准。
- 员工关闭每日缺勤检查导致的 `cancelled` 请求同样只进入历史。

## 错误处理与交互

- API 返回 400：拒绝原因为空或请求格式错误。
- API 返回 403：管理员无目标店铺权限。
- API 返回 404：请求不存在或不属于 URL 店铺。
- API 返回 409：请求已经被 Telegram 或另一管理员处理。
- 前端批准前使用确认框，避免误触。
- 拒绝输入取消时不发送请求；空白时提示必须填写。
- 操作成功后重新加载本页，记录从待审批移动到历史，汇总同步刷新。
- 操作失败时沿用现有后台错误提示和按钮 busy 状态，不乐观修改表格。

## 多语言与视觉

增加中文、英文、越南文和俄文文案，至少覆盖：

- 缺勤审批导航和标题。
- 待审批缺勤、审批历史。
- 通知状态。
- 批准罚款、拒绝原因必填。
- 已处理提示和状态标签。

复用现有表格、卡片、颜色变量和按钮样式。状态使用克制的小标签或文字，不引入新的 UI 依赖。

## 测试与验收标准

1. 远程已经存在的待审批缺勤在上线后可以直接显示，不需要迁移或重新生成。
2. 管理员只能查询和操作有权限店铺的请求。
3. 店铺、员工、日期和状态筛选同时作用于列表与汇总。
4. 待审批和历史分别分页、排序，汇总不受分页影响。
5. 通知状态正确反映已发送、未入队和待重试。
6. 后台批准生成一条且仅一条可编辑缺勤罚款。
7. 后台拒绝必须填写原因，拒绝后不生成罚款。
8. Telegram 与后台并发操作时只有第一个成功。
9. 已取消请求不能批准或拒绝。
10. 历史中的实际罚款读取当前 `income_records.fine`。
11. 多币种罚款总额分币种显示，不直接相加。
12. 四种后台语言均有可读文案。
13. 桌面和窄屏下页面保持现有后台视觉和横向滚动行为。
14. 原有 Telegram 审批、签退审批、考勤统计、请假联动和员工免检测试继续通过。
