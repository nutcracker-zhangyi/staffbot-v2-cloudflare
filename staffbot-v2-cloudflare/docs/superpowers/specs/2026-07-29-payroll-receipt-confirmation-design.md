# 工资收款确认回执设计

日期：2026-07-29

## 目标

员工点击“确认已收到”后，原工资确认消息应变成一份可追溯的工资收款回执，
清楚说明：

- 谁确认收到工资；
- 属于哪一家店铺；
- 属于哪个工资周期；
- 工资总额及实际付款方式拆分；
- 何时确认；
- 对应哪一笔工资记录。

本次只改善确认后的 Telegram 消息，不改变工资计算、付款、凭证、邮件或
Dashboard 逻辑。

## 已确认决定

- 回执显示员工姓名和 Telegram ID，避免同名员工无法区分。
- 回执显示工资周期的开始时间和截止时间。
- 时间统一使用员工所在店铺的时区。
- 回执显示工资总额。
- 回执显示银行卡、USDT、现金的实际付款拆分。
- 金额为 0 的付款方式不显示。
- 回执显示员工实际点击确认的时间。
- 回执显示工资 ID，方便后台、数据库和日志检索。
- 原工资确认消息直接更新为回执，不额外发送重复消息。
- Telegram 按钮弹窗只显示简短的确认成功提示。
- 中文、英文、越南语和俄语保持一致。

## 不在本次范围

- 不修改工资周期或工资金额的计算规则。
- 不修改中午 12 点的工资截止点。
- 不修改收入归属周期的边界规则。
- 不修改管理员付款拆分和付款凭证流程。
- 不修改财务邮件的内容或发送条件。
- 不向管理员额外发送一条 Telegram 确认通知。
- 不新增或修改数据库表、字段和迁移。
- 不在回执中显示银行卡账号、USDT 地址、二维码或付款凭证。

## 员工看到的回执

中文示例：

```text
✅ 工资收款已确认

员工：Alice
Telegram ID：1001
店铺：Tokyo Club

工资周期：
2026/07/30 12:00 至 2026/08/13 12:00

工资总额：₫8,000,000
银行卡：₫5,000,000
USDT：₫3,000,000

确认时间：2026/08/13 20:15
工资 ID：PAYROLL:DEFAULT:8467459276:2026-08-13
```

如果现金金额大于 0，则在付款拆分中增加现金一行。如果某种付款方式金额为
0，则不显示该行。

## 字段来源

| 回执字段 | 数据来源 | 回退规则 |
| --- | --- | --- |
| 员工 | `store_members.display_name` | Telegram 姓名、用户名、Telegram ID |
| Telegram ID | `payroll_disbursements.telegram_id` | 无 |
| 店铺 | `stores.name` | 无 |
| 工资周期开始 | `payroll_disbursements.period_start` | 无 |
| 工资周期截止 | `payroll_disbursements.cutoff_at` | 无 |
| 工资总额 | `amount_snapshot_micros` | 无 |
| 银行卡 | `bank_micros` | 0 时不显示 |
| USDT | `usdt_micros` | 0 时不显示 |
| 现金 | `cash_micros` | 0 时不显示 |
| 确认时间 | `confirmed_at` | 无 |
| 工资 ID | `payroll_id` | 无 |

工资金额继续使用工资记录里的币种和现有金额格式化函数。所有 micros 字段只在
展示时换算，不重新计算工资。

## 周期和时间语义

- `period_start` 是该工资周期的开始边界。
- `cutoff_at` 是该工资周期的截止边界。
- 截止点之前产生的收入属于本回执对应周期；截止点当时及之后产生的收入属于
  下一个周期。
- 两个时间都转换成店铺时区后显示到分钟。
- `confirmed_at` 同样转换成店铺时区后显示到分钟。

因此，回执展示的是工资记录已经固定保存的周期快照，不根据员工点击确认的
时间重新推算周期。

## Telegram 交互

员工点击“确认已收到”后：

1. 继续调用现有确认逻辑，写入工资记录、财务邮件 outbox、审计日志和
   `confirmed_at`。
2. 确认成功后，读取包含员工、店铺和时区信息的完整工资记录。
3. 将带按钮的原消息编辑成完整回执。
4. 编辑后不再保留“确认已收到”和“付款有问题”按钮。
5. callback 弹窗只显示简短的“确认成功”，避免 Telegram callback answer
   字数限制和重复显示整份回执。

如果确认数据库事务失败，继续使用现有“暂时无法确认收款，请联系管理员”
错误提示，且不把原消息改成成功回执。

如果工资已经被处理，继续使用现有“该请求已处理”提示，不重复生成工资记录。

## 查询与代码边界

现有确认函数已经返回确认后的 `payroll_disbursements` 行。本次为该返回结果
补充只读关联数据：

- 店铺名称；
- 店铺时区；
- 员工显示姓名。

回执渲染使用独立的小型格式化函数，复用：

- 现有 i18n `render` / `t`；
- 现有工资金额格式化；
- 现有店铺时区日期格式化。

不在 Telegram handler 内重新查询或汇总收入流水，也不复制工资计算逻辑。

## 多语言

新增或扩展以下两类文案：

- 完整工资收款回执模板；
- 简短 callback 确认成功提示。

四种语言使用相同字段和相同顺序：

1. 员工；
2. Telegram ID；
3. 店铺；
4. 工资周期；
5. 工资总额；
6. 非零付款拆分；
7. 确认时间；
8. 工资 ID。

## 隐私与可追溯性

- 回执只发送给工资记录对应的员工。
- 显示 Telegram ID 和工资 ID，用于唯一识别和追溯。
- 不显示完整银行卡账号或 USDT 地址。
- 不重复发送付款二维码或凭证。
- 不在日志中新增支付账号、二维码或凭证内容。

## 测试策略

### Telegram 流程测试

- 员工确认后，工资状态变成 `confirmed`。
- 原消息被编辑为完整回执。
- 回执包含员工姓名和 Telegram ID。
- 回执包含店铺名称。
- 回执包含店铺时区下的周期开始和截止时间。
- 回执包含工资总额。
- 回执包含所有非零付款拆分。
- 回执不包含金额为 0 的付款方式。
- 回执包含店铺时区下的确认时间。
- 回执包含工资 ID。
- callback answer 使用简短成功提示，而不是完整回执。

### 回归测试

- `salary_records` 仍只生成一条。
- `payroll_email_outbox` 仍只生成一条。
- 重复点击不重复确认。
- 确认失败时不显示成功回执。
- 付款争议流程不受影响。
- 四种语言模板都能替换全部占位符。

## 验收标准

在 staging 使用一笔包含银行卡和 USDT 拆分的工资完成确认后：

- 员工能从 Telegram 消息直接看出本人、店铺、工资周期、总额和拆分；
- 消息包含确认时间和工资 ID；
- 原确认按钮消失；
- 管理后台中的工资状态、工资记录和财务邮件 outbox 与修改前保持一致；
- 全部自动化测试通过；
- production 不发生任何变化。
