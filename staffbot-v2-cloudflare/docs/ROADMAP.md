# 开发路线图

状态说明：

- ✅ 已完成并有测试覆盖
- 🧪 已在 staging 验证
- ⏳ 待单独评审和批准
- ⬜ 尚未开始

## 已完成的业务阶段

### Phase 1：收入与罚款基础流程 ✅

- 员工提交收入
- 管理员审批或拒绝
- 已批准金额进入工资计算
- 管理员操作审计

### Phase 2：工资申请与付款记录 ✅

- 员工查看当前工资
- 员工提交工资请求
- 管理员批准或拒绝
- 记录实际支付金额和工资周期
- 支付完成后推进员工周期起点

### Phase 3：考勤与请假 ✅

- 上班、下班与待审批下班流程
- 请假申请
- 缺勤识别和罚款审批
- 店铺时区边界

### Phase 4：多语言与店铺配置 ✅

- Telegram 多语言文案
- 店铺级时区、币种及业务设置
- 员工与店铺成员关系

### Phase 5：管理员页面 ✅

- 申请与记录查询
- 管理操作入口
- 筛选、排序和审计信息

## 基础架构阶段

### Phase 6：模块化重构 ✅

- 拆分 Worker 入口、工作流和服务模块
- 建立统一测试入口和类型检查
- 保持既有业务行为

### Phase 7：统一工资账本 staging 验证 🧪

- 新增不可变 `payroll_entries`
- 统一使用 `amount_micros` 保存参与工资计算的最终金额
- 使用 `type` 区分收入、罚款、预支、调整和冲正
- 建立来源幂等、冲正和审计约束
- 完成 staging 迁移预检和历史回填
- 完成重复回填、旧表对账、影子读取和双写审批验证
- staging 已切换为 `dual + ledger`

验证证据：

[2026-07-28 staging payroll ledger migration report](./reports/2026-07-28-staging-payroll-ledger-migration.md)

### Phase 8：production 统一账本切换 ⏳

本阶段尚未执行。开始前需要单独批准以下内容：

1. production 迁移与备份窗口；
2. 历史数据预检和异常记录处理；
3. `dual + legacy` 观察期；
4. `dual + shadow` 对账标准；
5. `dual + ledger` 切换与回滚负责人。

不得因为 staging 已通过就自动合并、部署或切换 production。

## 下一批产品阶段

### Phase 9：收入 dashboard 🧪

目标：

- 按月份、店铺和员工查看收入与扣款；
- 使用图表比较员工和月份；
- 所有汇总金额来自统一工资账本；
- 清楚区分收入、罚款、预支、调整和实际付款。

开始实施前需要单独评审：

- 指标定义和币种处理；
- 管理员权限和数据范围；
- 图表与明细的查询接口；
- 大数据量下的性能方案；
- 验收样例和发布方式。

### Phase 10：员工个人发薪流程 🧪

目标范围包括：

- 新员工选择开始算工资的第一天；
- 按个人周期第 16 天和第 30 天提醒发薪；
- 固定工资截止点；
- 账号、现金等付款方式及比例；
- 多张付款凭证；
- 员工确认收款；
- 邮件通知；
- 确认付款后开始下一个工资周期。

代码、数据库迁移和管理后台已经部署到 staging。自动工资页面、旧数据隔离、
本地测试和 staging 数据库结构检查已经通过；真实 Telegram 付款闭环、邮件发送
和临时 Cron 验收仍待单独授权或配置，因此本阶段保持 `🧪`，不得进入 production。

已确认规格与实施计划：

- [个人发薪流程实施计划](./superpowers/plans/2026-07-29-personal-payroll-cycle.md)
- [staging 个人发薪流程验收记录](./reports/2026-07-29-staging-personal-payroll-validation.md)

## 明确不在当前批次内

- production 数据迁移或部署
- dashboard 代码
- staging Cron 启用和真实自动提醒
- 未配置发件人与财务收件人的真实邮件发送
- 修改已确认的工资账本数据契约

个人发薪流程完成 staging 全链路验收并获得明确上线批准前，以上边界保持不变。
